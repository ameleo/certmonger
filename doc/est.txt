Certificates can be requested from servers which implement Enrollment over
Secure Transport (EST), as described in RFC 7030, using the bundled
"est-submit" helper.  Like SCEP, there's no concept of a "default" EST
server for the system, so a CA configuration needs to be added:

  getcert add-est-ca -c exampleESTca -u https://est.example.com/ \
    -R /etc/pki/est-server-ca.pem

The "-R" option names a file containing the certificate of the CA which
issued the EST server's TLS certificate.  If it is not given, the system's
trusted CA certificates are used.  If the server serves more than one CA
under different labels, the label can be given with the "-i" option.

The helper uses the server's "cacerts" interface to retrieve the CA's
certificates, its "simpleenroll" interface to obtain a first certificate,
and its "simplereenroll" interface to renew it.

Servers usually require a client to authenticate itself before they issue
it a first certificate.  The helper supports HTTP Basic authentication, and
uses the challenge password given to "getcert request" with its -L or -l
option as the password.  When no user name is set with the "-U" option of
"getcert add-est-ca", a challenge password of the form "name:password"
supplies both:

  getcert request -c exampleESTca -k /etc/pki/tls/private/host.key \
    -f /etc/pki/tls/certs/host.crt -G EC -g 256 -N CN=host.example.com \
    -L device1:onetimesecret

A password which is the same for every request can instead be stored in a
file named with the "-W" option of "getcert add-est-ca".

Renewal requests are authenticated using TLS client authentication with the
current certificate and its private key, so no password is needed once a
certificate has been issued.  To make this possible, the daemon tells the
helper where the private key is stored (see helpers.txt).  The helper
always connects using libcurl, built with OpenSSL.  Keys in PEM files are
read by libcurl itself.  Keys in NSS databases, including keys in hardware
tokens or TPMs which are accessible through an NSS database, are located
using NSS and then used through OpenSSL's PKCS#11 provider (the
"pkcs11-provider" package, which requires OpenSSL 3), which loads the same
PKCS#11 module that NSS uses for them: the NSS software token for keys in
the database itself, or the token's module.  The helper loads and
configures the provider by itself, so no change to the system's OpenSSL
configuration is needed.  Either way, the server's certificate is verified
by OpenSSL, against the CA certificates given with "-R", or, if none were,
those which libcurl trusts by default.

If the server answers that a request is awaiting approval, the helper asks
the daemon to send it again after the delay which the server suggests.
