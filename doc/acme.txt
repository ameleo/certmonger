Certificates can be requested from servers which implement the Automatic
Certificate Management Environment (ACME) protocol, as described in RFC
8555, using the bundled "acme-submit" helper.  Like SCEP and EST, there's no
concept of a "default" ACME server for the system, so a CA configuration
needs to be added, naming the server's directory:

  getcert add-acme-ca -c exampleACME -u https://acme.example.com/directory \
    -R /etc/pki/acme-server-ca.pem

The "-R" option names a file containing the certificate of the CA which
issued the server's TLS certificate.  If it is not given, the system's
trusted CA certificates are used.

Accounts
--------
The helper creates an account with the server the first time it is used,
with an ECDSA P-256 account key which it generates, and reuses that account
for every later order, renewals included.  The account key and the
account's URL are kept in a directory of their own, named after a digest of
the directory URL, under /var/lib/certmonger/acme (the value of the
CERTMONGER_ACME_DIR environment variable, or the helper's "-s" option, can
name another location).  The files are only readable by the daemon's user.

Servers which only issue certificates to clients they know require an
external account binding (RFC 8555, 7.3.4): the CA hands out a key
identifier and a MAC key, and the client signs its account key with that MAC
key when creating its account.  These can be configured for the CA:

  getcert add-acme-ca -c exampleACME -u https://acme.example.com/directory \
    --eab-kid kid1 --eab-key-file /etc/pki/acme-eab.key

where the file holds the base64url-encoded MAC key, or given with each
request, as its challenge password in the form "KID:KEY", which is useful
when the CA issues them for one use only:

  getcert request -c exampleACME -k /etc/pki/tls/private/host.key \
    -f /etc/pki/tls/certs/host.crt -G EC -g 256 -N CN=host.example.com \
    -D host.example.com -L kid1:b64urlmackey

Note that the daemon also adds the challenge password to the signing
request, which the helper sends to the same CA; a key file avoids that.

Orders and challenges
---------------------
An order names the DNS names and IP addresses (RFC 8738) in the signing
request's subjectAltName extension, or its subject's common name if it has
none.  The helper doesn't serve content, so it can't answer the "http-01"
or "tls-alpn-01" challenges.  It answers "dns-01" challenges when it is
given the means to update the DNS (see below), and "device-attest-01"
challenges when it attests the device.  Otherwise it is meant for CAs which
authorize accounts by other means, such as an external account binding,
whose authorizations are valid as soon as the order is placed.  The helper
finalizes the order with the daemon's signing
request, waits for the certificate while the server processes the order,
following its Retry-After suggestions, and, if that takes longer than a
minute and a half, hands the order's URL back to the daemon as a cookie, so
that it checks on the order again later.

DNS challenges
--------------
With a TSIG key, or GSS-TSIG, the helper answers "dns-01" challenges (RFC
8555, 8.4) itself, with DNS UPDATE messages (RFC 2136), without running
any other program:

  getcert add-acme-ca -c exampleACME -u https://acme.example.com/directory \
    --tsig-key-file /etc/pki/acme-dns.key

For each name of the order, it:

* takes _acme-challenge.<name>, without the "*." label of a wildcard name,
  and follows the CNAME there if there is one, so that the record can be
  delegated to a zone which is set aside for the purpose;

* finds the zone of that name, looking up SOA records from the name
  upwards, or uses the one given with "--dns-zone";

* sends an update which adds a TXT record holding the base64url-encoded
  SHA-256 digest of the challenge's key authorization, with a TTL of 60
  seconds, to the zone's primary server (the SOA record's MNAME), or to the
  one given with "--dns-update-server HOST[:PORT]";

* asks each of the zone's name servers (the NS records' names, each of
  their addresses), or the servers given with "--dns-check-servers
  HOST[:PORT],...", directly, until all of them serve the record, for at
  most two minutes, or the time given with "--dns-wait SECONDS";

* tells the CA that the challenge can be checked, and waits until it has;

* removes the record, whatever happened, with another update.

Lookups go to the system's resolvers, or to the one given with
"--dns-resolver ADDRESS[:PORT]", which also serves to find the addresses of
the servers named in the DNS.

Updates are signed using TSIG (RFC 8945) with a shared key, read from the
file given with "--tsig-key-file", in the form in which BIND's tsig-keygen
and ddns-confgen write them:

  key "acme" {
          algorithm hmac-sha256;
          secret "base64...";
  };

or, on one line, in the form which nsupdate's -y option takes:
"[algorithm:]name:secret".  The algorithms are hmac-sha256 (the default),
hmac-sha384, hmac-sha512 and hmac-sha224.  The file is read each time the
helper runs, and the key never appears in its output.  With BIND, the key
can be allowed to change only TXT records of the zone:

  update-policy { grant acme zonesub TXT; };

or only the names which it is meant for.

With "--gss-tsig", updates are signed using GSS-TSIG (RFC 3645), as the
DNS servers of FreeIPA and Active Directory accept them from the hosts of
their domain: the helper obtains Kerberos credentials with the host's keytab
(the default keytab, usually /etc/krb5.keytab, or the one given with
"--keytab"), for its first principal (or the one given with "--principal"),
in a credential cache of its own, and sets up a key with the server, whose
name must be known (the SOA record's MNAME, or a name given with
"--dns-update-server"), in TKEY queries, for its "DNS/<server name>"
principal.  A server running BIND can let each host change the records
under its own name:

  update-policy { grant EXAMPLE.COM krb5-selfsub . TXT; };

The helper waits for the CA to check the record for up to two minutes; if
the CA takes longer, the record is removed nonetheless, and the
authorization will likely fail, and be tried again with a new order.  If
the helper is killed while a record is published, the record stays.

Device attestation with a TPM
-----------------------------
With "--attest tpm", the helper requests the device's permanent identifier
(draft-ietf-acme-device-attest), which is the value given with
"--permanent-identifier", or else the common name of the request's subject,
and answers the server's "device-attest-01" challenge with a WebAuthn
attestation object of the "tpm" format (WebAuthn, 8.3), which proves that the
private key of the request was generated in, and never leaves, the device's
TPM.

The private key must be generated in the TPM by the daemon, through the
tpm2-pkcs11 PKCS#11 module, in a token which is accessible through an NSS
database:

  modutil -dbdir /etc/pki/device -add tpm2 \
    -libfile /usr/lib64/pkcs11/libtpm2_pkcs11.so
  getcert add-acme-ca -c device -u https://acme.example.com/directory \
    --attest tpm
  getcert request -c device -d /etc/pki/device -t certmonger -n device \
    -p /etc/pki/device/pin -G RSA -g 2048 -N CN=device42 \
    -L kid1:b64urlmackey

How it works:

* An attestation key (AK), a restricted signing key, is created under the
  TPM's endorsement key (EK) the first time it is needed, and kept in the
  account's directory (ak.pub and ak.priv, which only that TPM can load).
  It is an RSA-2048 key if the TPM has an RSA EK certificate, and a P-256
  key otherwise.

* The AK is certified by the CA's attestation key certification service,
  next to the directory (<directory URL without its last segment>/attest/v1/
  ak/begin and finish).  The helper sends the EK's certificate, read from the
  TPM's non-volatile memory, the certificates of the CAs which issued it,
  which the TPM keeps there too (TCG EK Credential Profile 2.0, 2.2.1.5), or
  else which the certificate's authorityInfoAccess extension names, the AK's
  public area, and a MAC of it with the external account binding's key.  The server answers with an HMAC key
  which it encrypted to the EK: only that TPM can import it.  The helper
  imports it under the EK, certifies the AK with it (TPM2_Certify, with the
  server's nonce), and the server, having checked the statement, issues a
  certificate for the AK.  This does not rely on TPM2_ActivateCredential,
  so that a TPM which can be made to certify an external object (TCG VRT0010)
  cannot fool it.  The AK's certificate is kept (ak.crt), and renewed when
  less than 30 days of its validity remain.

* For each order, the helper finds the request's key in the token, loads it
  in the TPM, and has the AK certify it (TPM2_Certify), with the SHA-256
  digest of the challenge's key authorization (RFC 8555, 8.1) as qualifying
  data: draft-ietf-acme-device-attest uses the key authorization as
  "attToBeSigned", and the attestation object has no "authData".  The
  attestation statement carries the AK's certificate and chain ("x5c"), the
  statement ("certInfo"), its signature ("sig"), and the key's public area
  ("pubArea").  "sig" is the TPMT_SIGNATURE which TPM2_Certify returns, as
  WebAuthn (8.3) defines it.  Some authenticators (Windows Hello among
  them) send the bare signature which it holds instead; a server which
  accepts only that form will refuse the helper's attestation.

Getting hold of the key in the TPM: PKCS#11 has no notion of TPM2_Certify,
which needs the authorization value of the key which is certified, and
tpm2-pkcs11 gives each key a random one, encrypted with a token-wide
wrapping key which is sealed in the TPM under the user PIN.  The helper
reads the key's TPM blobs and encrypted authorization value through
PKCS#11, where tpm2-pkcs11 exposes them as vendor attributes, and the
token's primary key and sealed wrapping key from the module's store (an
SQLite database), and then does what the module does when the user logs
in.  This ties the helper to that store's format.  The alternative, having
the helper generate the key itself and add it to the token, would tie it to
the same format for writing, and would take key generation away from the
daemon.  Tokens whose primary key is not persistent (tpm2_ptool init
--transient-parent) are not supported.

The TPM is reached using the TSS's TCTI loader: by default the TCTI named
in the TPM2_PKCS11_TCTI environment variable, which tpm2-pkcs11 also uses,
then TPM2TOOLS_TCTI, then the TSS's default (the resource manager, or
/dev/tpmrm0).  The endorsement hierarchy must not have a password.  The key's
authorization value is only ever used through HMAC sessions, and the
wrapping key is unsealed through a session salted with the token's primary
key, so that neither goes to the TPM in the clear.

TPMs which don't keep their EK certificate in their non-volatile memory,
such as some firmware TPMs whose manufacturer serves it online, are not
supported yet.

Building the helper with TPM support needs tpm2-tss (libtss2-esys,
libtss2-mu, libtss2-rc and libtss2-tctildr) and SQLite; configure's
--with-tpm2 option makes them required, --without-tpm2 leaves them out.
